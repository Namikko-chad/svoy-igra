# Архитектура

```
 apps / browsers ────┐  REST /api/*        ┌──────────────── backend ─────────────────┐
 (player/host/admin) ├────────────────────►│ api ──► packs.Store ──► DATA_DIR/packs/  │
                     │  WS /api/ws?token=  │  │                                        │
 Android TV / screen ├────────────────────►│ ws.Hub ◄─► game.Manager ─► games/*.json │
                     │  UDP 3051 probe     │                                          │
 apps / TV  ─────────┴────────────────────►│ discovery                                │
                                           └──────────────────────────────────────────┘
```

## Компоненты (связываются в `backend/app/server.go`)

| Компонент | Ответственность |
|---|---|
| `packs.Store` | библиотека паков на диске; CRUD для редактора; импорт/экспорт `.dub`; медиафайлы |
| `game.Manager` | все текущие игры: создание, поиск по PIN или токену, сохранение изменённых игр каждую секунду, удаление игр, простаивающих `GAME_IDLE_MINUTES` |
| `game.Engine` | одна игра: идентичность (PIN, PIN админа, токены ролей, слот ведущего, присутствие), фазы, таймеры, кнопки каждого игрока, очки, представления по ролям; сохраняется в `games/<id>.json` |
| `ws.Hub` | аутентифицирует сокеты по ролям, передаёт команды движку, отправляет каждому сокету его собственное состояние, измеряет RTT |
| `api` | REST: создание/список/вход в игры, библиотека и редактор паков (блокировка, копирование), медиа, скачивание/загрузка файла игры, `assetlinks.json` |
| `discovery` | отвечает на широковещательные UDP-запросы именем и портом сервера |
| SPA-обработчик | опционально: раздаёт собранный веб-клиент, если задан `STATIC_DIR` |

## Поток данных

1. Клиент создаёт игру (`POST /api/games`, становится её админом) или входит в игру по PIN
   и роли (`POST /api/games/{pin}/join`) и сохраняет токен. Токен принадлежит одной
   игре и одной роли.
2. Он открывает `/api/ws?token=…`; хаб сопоставляет токен с его игрой и ролью и отправляет
   `welcome` и полный `state`.
3. Команды идут через сокет. Движок проверяет их по роли и фазе,
   меняет состояние и записывает историю.
4. После каждого изменения хаб заново строит представление **для каждого получателя** — роль определяет,
   что видно (ответ — только ведущему до показа; админ никогда не видит
   вопросов), — и отправляет его. Диффов нет: каждый `state` — полный снимок.
5. Таймеры (время чтения, кнопка каждого игрока, окно нажатия) работают в движке. Когда
   открывается кнопка игрока, сервер отправляет этот момент; клиенты только отображают его.
6. Каждые 2 с хаб пингует каждый сокет; pong даёт RTT, который видит админ и
   использует автоматическая компенсация задержки.

## Жизненный цикл

- **Запуск:** чтение конфигурации → проверка `DATA_DIR` → открытие библиотеки паков → загрузка всех
  `games/*.json` (вопрос в процессе восстанавливается как табло; отсутствующий пак переводит
  эту игру в лобби) → запуск хаба, цикла менеджера и обнаружения → прослушивание.
- **Работа:** движок помечает себя изменённым при каждом изменении; менеджер атомарно записывает изменённые
  игры не чаще раза в секунду и каждые 15 с удаляет игры, у которых не было
  сокетов в течение `GAME_IDLE_MINUTES` (файл и токены; сокеты закрытой игры получают `4004`).
- **Остановка (SIGINT/SIGTERM):** сокеты закрываются, каждая игра записывается в последний раз,
  HTTP-сервер завершает работу, базы данных паков закрываются.

## Конкурентность

У каждого движка свой мьютекс; игры никогда не разделяют состояние, кроме библиотеки паков. Вызовы хуков (состояние изменилось, событие, отзыв токенов) собираются,
пока он захвачен, и доставляются после освобождения, поэтому хаб может читать представления без
взаимоблокировок. Каждый таймер несёт номер поколения и игнорируется, как только игра ушла дальше.
У каждого сокета своя очередь записи; клиент, который не успевает, отключается.
